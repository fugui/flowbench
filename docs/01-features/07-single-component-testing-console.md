## 1. 业务背景与问题痛点分析 (Problem Statement)

在 Milestone 9 之前，`flowbench Monitor Studio` 偏向**“底层网络协议/内核 eBPF 基础设施开发者”**视角：
1. **帧头字节喧宾夺主**：界面默认以 24 字节帧头色块矩阵（Magic、CRC32、Length、Hex Dump）占据 60% 黄金视觉区域，而业务开发最关心的 Protobuf 业务明文字段被严重挤压边缘化。
2. **代理网络黑话隔阂**：调用记录中充斥着 `Ingress`、`Egress` 等代理方向术语，顶部拓扑甚至将 `eBPF 出站自愈引擎` 作为独立业务大卡片呈现，无法直观反映**“上游业务调用方 (Caller) ──▶ 被测服务 (SUT) ──▶ 下游依赖后端 (Backends)”**的真实微服务业务模型。
3. **因果与时序关系缺失**：单组件处理一笔业务请求时，多次下游调用的先后顺序、串行/并行关系、下游请求与响应之间的成对往返被拍扁，缺乏时序因果追踪能力。

为了彻底赋能**“正在开发与调试单个业务组件（SUT）的业务开发人员”**，本特性规范全面重塑工作台交互流：
- **以业务 Protobuf 字段为核心**：底层 24B 二进制帧头与 Hex 默认折叠，只在协议排障或校验异常时按需展开；
- **经典 UML 时序图呈现**：基于垂直生命线（Caller、SUT、下游组件列表）与水平消息箭头（实线请求 `──▶` 与虚线响应 `◀──`），一目了然呈现调用因果与耗时；
- **智能下游组件命名识别**：优先显示用户配置的微服务别名（如 `风控中心 credit-svc`），兜底采用精准 `IP:Port`；
- **一体化单组件测试与 Mock 闭环**：点击 UML 时序图中的任一步骤，原地查看/修改业务 JSON 入参或下游 Mock 返回，一键重放并呈现高亮字段级 Diff。

## 2. 需求功能矩阵 (Feature Matrix)

| **UML-01** | 端到端调用 UML 时序图数据模型与生命线生成 | `internal/monitor` | **P0** | 1. 扩展调用事务关联逻辑，为每个 `TransactionTrace` 自动派生标准 UML 时序步骤列表（`UMLSteps`）；<br>2. 自动提取参与者生命线（`Participants`）：第 1 列固定为 `Caller (业务调用方)`，第 2 列居中高亮为 `SUT (被测组件)`，后续各列为按交互顺序识别的下游组件（`BackendEndpoint`）；<br>3. 准确计算步骤序号（`①, ②, ③...`）、耗时、消息方向（`Caller -> SUT`、`SUT -> Backend`、`Backend -> SUT`、`SUT -> Caller`）及往返类型（同步调用实线 `──▶` vs 响应返回虚线 `◀──`）。 | 针对包含下游查询的调用事务，生成的 UMLSteps 顺序完整、源与目标组件匹配无误，返回消息能正确标记 `IsReturn=true` 与下游耗时。 |

## 3. 非目标与约束边界 (Non-Goals & Constraints)

1. **Non-Goal**：不引入重量级庞大的第三方前端框架（如 React/Vue/Node.js 构建链），继续依托单 Go 二进制内嵌的原生高效 DOM 与 CSS 实现，零编译依赖，保持纯粹安全。
2. **Non-Goal**：不改变三级微服务自定义 TCP + Protobuf 协议栈核心，不侵入用户业务代码。
3. **约束**：重放过程中继续遵循大端字节序、动态 RequestID 映射与 CRC32 自动重算自愈规则，底层复杂性由引擎自闭环。
